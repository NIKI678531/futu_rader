# ADR-0015 — 第五类成员：视图内聚合（`kolProfile` 不做端点）

- **状态**：已接受
- **日期**：2026-09-09
- **相关**：[ADR-0004](0004-radar-member-split.md)、[ADR-0003](0003-endpoint-granularity.md)、[docs/PRD.md](../PRD.md) §4.3 M5、[CLAUDE.md](../../CLAUDE.md) 铁律 1

## 背景

[ADR-0004](0004-radar-member-split.md) 把 `window.RADAR` 的成员分成四类：契约函数（后端）、口径常量（后端 `/meta`）、展示助手（前端永久保留）、演示生成器（必须消失）。

接 KOL 影响力页（工单 06）时发现 `kolProfile(name, posts, campFn?)` **一类都不属于**：

- 它不是展示助手 —— 它产出的是数字（篇数、自家/竞品篇数、互动合计、类型分布），不是颜色或文案。
- 它不是生成器 —— 没有伪随机，输入确定则输出确定。
- 它看起来最像契约函数，spec 里也确实提过 `GET /kols/{name}/profile`。但它做不成端点。

## 决策

**承认第五类：视图内聚合 —— 对接口已经下发的数据再数一遍，实现留在前端。**

目前唯一的成员是 `kolProfile`，实现在 `frontend/src/lib/profile.js`，逐字拷自设计源（唯一有意偏差见下）。`frontend/src/data/radar.js` 不暴露它，后端 `backend/core/kol.py` 明确不实现它。

判定标准（三条全中才算这一类）：

1. 输入**完全来自已经下发的响应**，不需要任何后端才有的数据；
2. 结果**必须随前端筛选重算**，因此没有一个稳定的 URL 能代表它；
3. 数的是「这批里有几个」，不是 PRD 第 3 章列举的那些口径公式。

## 理由

**做不成端点。** PRD §4.3 M5 逐字要求声量排名「随 ETF 与类型筛选变化、不随 KOL 筛选变化」。页面要的是**当前可见帖子子集**上的画像，而那个子集由四级级联筛选 × 类型多选 × `campRule` 开关在屏幕里算出来。要做成端点，就得把这套筛选语义在 Python 里再实现一遍 —— 那正是 [CLAUDE.md](../../CLAUDE.md) 明令禁止的「照着行为手推一遍」：任何一处对不齐，逐字比对就红，且极难定位。退一步做成「每次筛选变化都请求一次」也不行，[ADR-0003](0003-endpoint-granularity.md) 已经因为组合爆炸否掉了按筛选切端点。

**不违反铁律 1。** 铁律 1 管的是**口径公式** —— 讨论热度、评论去重、基准区间、情绪净值、赞踩比、环比、阶段合并、样本阈值。这里数的是「这批帖子里提自家的有几篇」，而「这批」按设计本来就该随筛选重算。真正属于口径的那一份 —— **全量** leaders —— 由后端在 `kolImpact(range)` 里算好随响应下发，KOL 详情页用的是那一份。两份并存是有意的：一份是「全区间的事实」，一份是「你现在看到的这些」。

## 后果

- **偏离工单 06 的验收标准 1 与 spec 的接口清单。** 两处都写了要给 `kolProfile` 暴露端点。以本 ADR 为准，工单 06 的 Comments 里记了这条偏差。PRD §5 的 23 组契约函数因此实际落成 **22 个端点**。
- **与镜像的分叉风险**，同 [ADR-0004](0004-radar-member-split.md) 对展示助手的那条：设计源改了 `kolProfile`，`lib/profile.js` 不会自动跟。对冲手段一样 —— 文件头写明来源，再导入流程里一并重拷。
- **合计对 `null` 有传染性，这是相对设计源的唯一有意偏差。** 设计源写 `eng += p.engagement`，而 JS 的 `+` 把 `null` 当 `0`：一篇取不到评论数的帖子会被静悄悄算成「那篇 0 条评论」，合计照样是个看着很正常、只是偏小的数字 —— 直接违反铁律 2，且比渲染成 `NaN` 坏得多，因为 `NaN` 一眼看得出坏了。改成「有一篇不知道，合计就是不知道」。演示数据里计数字段永远齐全，这一支不会走到，逐字比对因此仍然全绿；护栏是六态场景下的 `frontend/scripts/six-state.mjs` KOL ⑥ 与 `backend/tests/test_six_states.py::test_leader_totals_are_null_when_any_post_count_is_null`。
- **这一类会长大。** 产品监控与板块总览的筛选同样在前端，凡是「对已下发数据再数一遍」的都归这里。新增成员前先过上面那三条判定标准 —— 只要有一条不中，它就该是端点。

## 否决的备选

- **做成端点，把筛选条件当查询参数传上去**：组合爆炸（[ADR-0003](0003-endpoint-granularity.md) 已否），且要在后端重写一遍筛选语义。
- **屏内直接内联这段计算**：能跑，但那是把一段有明确身份的聚合藏进 890 行的屏幕里；下一个页面要同样的东西时只会被复制第二遍。
- **只用后端下发的全量 leaders，不再前端重算**：违反 PRD §4.3 M5 —— 筛到某只 ETF 之后，排名必须是那只 ETF 上的排名。
