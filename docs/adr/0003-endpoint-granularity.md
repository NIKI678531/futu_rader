# ADR-0003 — 端点粒度严格 1:1 于 PRD §5

- **状态**：已接受
- **日期**：2026-09-09
- **相关**：[plan.md](../../plan.md) §2.1（23 组函数 → REST 映射表）

## 背景

PRD 第 5 章定义了 23 组数据契约函数 ＋ 一行常量集合。前端接 API 时可以选择保持 1:1，也可以做页面级聚合端点（产品监控一屏要打约 12 个请求）。

## 决策

**严格 1:1**：PRD §5 每个函数对应一个 REST 端点，映射表见 [plan.md](../../plan.md) §2.1。不做页面级聚合端点。

前端自行做请求去重与缓存。

## 理由

1. **PRD §5 是甲方已确认的契约**。聚合会把 23 组契约揉进 5 个屏，真实通道接进来时「这个数归谁算」立刻含糊。
2. **六态是字段级的**（铁律 2）。聚合端点的顶层 `status` 表达不了「这块 ok、那块 low_sample、那块 unavailable」；硬要表达就得在响应里再造一套 per-block status——那就是 1:1，只是套了层壳。

内网只读工作台，12 个并发 XHR 不构成性能问题。

## 后果

- 产品监控首屏约 12 个请求，板块总览约 10 个。需要前端有一层并发 ＋ 去重 ＋ 缓存，这层是 [ADR-0005](0005-sync-shim-and-fidelity.md) 的垫片顺带提供的。
- 端点数量多（23 个），后端 `api/v1/` 下文件会不少。这是可接受的：每个文件对应 PRD 里一个可追溯的函数。

## 否决的备选

- **页面级聚合**（`/screens/product?code=&range=`）：见理由 2，六态表达不了。
- **首屏聚合 ＋ 交互增量**：兼具两者的缺点，且引入「哪些字段在首屏包里」这个新的、无处记录的隐性契约。
