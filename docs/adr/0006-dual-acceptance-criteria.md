# ADR-0006 — 两个 provider 各用一套验收标准

- **状态**：已接受
- **日期**：2026-09-09
- **相关**：[ADR-0001](0001-dual-provider.md)、[ADR-0005](0005-sync-shim-and-fidelity.md)

## 背景

[ADR-0001](0001-dual-provider.md) 定了两个 provider。它们的数值**本来就该不同**——`demo` 还原设计稿的演示数字，`mysql` 给真实数字。用同一套标准验会自相矛盾。

## 决策

### `demo` provider：可见输出 diff，机器判定

同一 URL 参数下，移植版（:5173）与设计源（:5174 的 `.dc.html`）渲染出的**可见文本与数值必须完全一致**。用 Playwright 抓两边 `textContent` 做 diff。

这是「100% 还原」唯一可证的形式——不做成机器可判的 diff，它就只是一句口号。

### `mysql` provider：不比数值，只验诚实性三条

1. 端点全部 **200**（数据缺失也返回 200，不返回 5xx）。
2. 真实存在的字段**有真值**。
3. 不存在的字段是 `null` ＋ 正确的 `status`，页面显示「暂不可用」——**而不是 0，也不是空白**。

第 3 条就是铁律 2 的可执行形式。

## 后果

- 需要引入 Playwright（前端 devDependency）。这是新增的工具链成本，换来的是「100% 还原」可回归、可 CI。
- 六态样本必须在测试里**钉死**：固定一组产品代码 × 区间，断言它们稳定命中每一态（`0` / `—` / `暂不可用` / `暂无内容` / `样本不足` / `待确认`），并断言序列化后 `null` 仍是 `null`。
  - 这些样本**镜像里已经存在**（`delta()` 的 `null` 分支、`candlesFor` 的 `status:'unavailable'`、`summaryFor` 的 `low`、`complianceFor` 三态、图片帖 `NO_TEXT`）。任务是**不弄丢**，不是新造。
  - 最容易弄丢的三个环节：JSON 序列化、Python 侧的 `or 0`、前端的 `?? 0`。

## 否决的备选

- **人工目视比对**：3000+ 行模板、五个屏、多个区间参数，人工比对既不可回归也不可信。
- **只验 `demo`**：真实通道通不通就永远不知道，风险整体推给第二期。
