## Comments

**验证**：后端 361 个测试（新增 58：`test_prices.py` 53、六态 3、`/meta` 阶段口径 2），六态红线 49 条（新增 4），五页 9 次逐字比对全部一致，4 条静态守卫，`npm run build` 干净。端点实测 22 条 `/api/v1` 路由 = 21 个契约端点 + `/meta`；另两个契约函数有意没有端点（`kolProfile` 随前端筛选重算，ADR-0015；`observe` 是 `pool().list` 的一个元素），加上不是端点的 `delta()`，24 个函数全部落地。

**这一单的 `null` 和别处的 `null` 不是一个量级。** 别处填错一格是数字不对，这里填错一格是**一张图**。K 线的四个价格字段缺失时全是 `None`，补成 0 之后画布上就是一根从 68 港元掉到 0 再弹回来的实体柱——它不报错、不缺格、不留白，是一张看着信息量很足的错图，而且是会被截图发到群里的那种。所以这一组从 provider 到门面一层不落地原样穿 `None`，`test_a_price_is_never_zero` 专门反过来钉「有值的价格永远 > 0」：补零的痕迹不会出现在 null 检查里，因为补出来的四个 0 照样「同生共死」。

**「休市」和「取不到」是两种空，页面上必须是两句话。** 7 天视图必然含一个周末，所以 `status == 'ok'` 的产品照样有两根空 K——那是**对的**，脚注说「非交易时段与休市日不补造 K 线」；没有行情源的产品整份 `unavailable`，挂徽章「价格数据暂不可用」并把脚注换成「当前产品价格数据暂不可用，不以指数或其他产品价格替代」。把后者的文案用到前者身上，等于每个周末都在报一次数据故障；反过来把前者用到后者身上，等于给一条根本不存在的价格线配了单位说明。六态里这两条是**互相 reject** 的一对，3469 演不可用、3033 演正常——只有一条方向的话，「所有产品都挂价格数据暂不可用」也能全绿，而那是把整个产品线的价格轨道一起关掉。

**阶段阈值不能放 /meta，因为它取决于粒度。** 半日粒度是 5、整日是 10（`stageHalfDay = ceil(lowSample / 2)`）。前端要是照着 /meta 的 `lowSample=10` 去判半日阶段，小时视图里几乎每一段都会被判成样本不足，整页阶段观点塌成一片灰——症状是「换了个阈值之后小时视图突然没有阶段了」，而没有任何东西会变红。所以它是**响应里的一个字段**，/meta 上那两个数只是它的取值来源。`unavailable` 态里这个键**整个不存在**（设计源的 `base` 上就没有），不是 0 也不是 null：没有阶段就没有判定，下发一个判不了任何东西的阈值只会让前端以为自己该拿它去判点什么。

**`stages.series` 与 `/heat-series` 是同一份数，这次的重复是有意的**，而且方向与 08 那次正好相反。08 砍掉 `ranks.list`、`pool.rankMap` 是因为**没人读**它们，留下唯一被读的那一份；这里被读的恰恰是内嵌的 `stages.series`（热度折线与阶段色带画在同一套几何上，拆成两次取数就是白挨一次串行往返），而 `/heat-series` 是**没有屏幕读**的那一个。它还得存在是因为 PRD §5 要求 24 个契约函数 1:1 对应端点。两者不会发散：演示期同一次 `heatSeriesFor()` 调用导出两份，真实期 `stagesFor` 的实现本身就调 `heatSeriesFor`，`test_stages_embed_the_same_series_the_heat_endpoint_returns` 逐字节比它们。

**阶段观点的四态在页面上是四块不同的内容，合并任意两块都会说出一个我们没得出的结论。** `unavailable` 是「AI 还没跑」（折线照常画，色带画不出来）；`empty` 是「区间内根本没人聊」；`low_sample` 是「有人聊、跑过了、只是不够下结论」；`ok` 才有观点。最容易被合并的是后两者——它们的 `stages` 长得几乎一模一样（都是 `category: null` 的灰段、都写「样本不足」），区别**全在 `series` 上**：`empty` 的每个点 mentions 都是 0。`test_empty_and_low_sample_differ_only_in_whether_anyone_talked` 钉的就是这个。三套缺数文案在这块面板上同时出现，还专门加了一条「阶段文本里永远不许出现『暂不可用』『暂无相关内容』」。

**相邻两段可以同分类，但只在吸并过孤立时段之后。** 我原本按「合并完相邻两段必然不同分类」写断言，600 份响应里红了 5 次。查下来全是 14 天以上视图的第二步合并：`A ｜ 孤立 ｜ A` 里那个孤立日被吸并之后，就留下两段挨着的 A——它们中间隔着一段被吞掉的日子，不是没合并干净。断言因此改成**限定版**：同分类相邻必须至少一侧 `absorbed > 0`。哪天第一步真的漏了，它照样会红。这类「例外是真的、但要写清楚例外的边界」比直接删掉断言值钱。

**六态场景层是按键覆盖的，这件事第二次咬人。** 演示池里本来就有两只没有行情源的产品（3406／3087）和一只阶段未生成的（3007），但六态 `pool.json` 只给了 `d7` 一个键，整份 d7 池就被换成那 8 只——`?code=3406` 会打开一个池里不存在的产品，页面在离六态十万八千里的地方炸。所以这两态得搬到池内产品（3469）身上。搬 K 线是**整份拷贝**供体响应（那份响应里没有一个字段与产品有关：桶标签来自 `buildRange`、币种是 null、note 是同一句话，脚本里加了断言钉住这一点）；搬阶段则**不拷贝**，而是拿 3469 自己的响应改 `status`、清空 `stages`、删掉两个判定键——`series` 是它自己的热度序列，是真数据，换成别人的就是在页面上画另一只产品的折线。

**新加的两条六态断言做了负向验证。** 把两份 sixstate fixture 移开重跑，恰好红出 6 条、全部落在这两个 case 上（想要的字没有、不该有的字在）。这一步不是多余的：`open` 钩子那类假绿已经踩过三次，「断言通过」和「断言有在断言」是两回事，而唯一能分辨的办法是让它真的红一次。

**没做的**：`heatSeriesFor` / `dailyFor` 有端点、有测试，但门面层**没有包装函数**——五个屏幕没有一处读它们（验过），加个没人调的门面成员只会让工单 12 删镜像时多一个需要判断的东西。`dailyFor` 在演示期与 `candlesFor` **不同源**：3406 在 `/candles` 上没有价格，在 `/daily` 上却有 42 天的 OHLC。这是设计源演示生成器的两条独立数据路径，第一期没有屏幕读 `/daily` 所以不影响任何页面，但接真实库时两者必须并到同一张行情表上，否则同一只产品的价格在两个端点上会对不上——`test_daily_rows_are_complete` 的 docstring 里记了这件事。
